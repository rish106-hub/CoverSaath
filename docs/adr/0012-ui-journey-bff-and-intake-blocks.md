# ADR 0012: UI journey, BFF boundary and intake blocks

Status: proposed (2026-10-31). Synthetic data only. All consent, privacy and notice wording named here is DRAFT and needs legal review. Related: ADR 0011 (hosting), `docs/exec-plans/active/ui-journey.md`.

## Context

CoverSaath has no frontend. The website repository holds a Next.js BFF and the UI. The API sends no CORS headers and rejects unknown Host and Origin values, so a browser can never call it. The UI journey needs: sign-in, a list of the caller's own cases and permissions, a member-card document kind, a registry of intake channels, and later read-back of values and passages.

## Decisions

- **D1. The BFF is the only client.** The browser never calls `/api/v1`. The BFF calls it server to server. Host, Origin, CORS, rate-limit and session-TTL logic do not change.
- **D2. Intake connector registry.** `src/contracts/intake-connectors.js` holds 10 frozen descriptors (upload, camera, email_forward, gmail, outlook, insurer_portal, hr_portal, digilocker, whatsapp, voice). Only upload is `available`; camera, email_forward and voice are `stub`; the rest are `later`. Stubs in `src/integrations/intake/` fail closed with `UnconfiguredConnectorError` and make no network call. `GET /api/v1/integrations` lists them with health and reports `documentScan.mode`.
- **D3. Identity sessions (built in run V1a; U1 approved).** Expand-only migration 017 adds `auth_identities (id, adult_user_id, issuer, subject_sha256, created_at, last_used_at, revoked_at)` with `UNIQUE(issuer, subject_sha256)`, an index on `adult_user_id` and RLS on; no existing table changes. `POST /api/v1/identity-sessions` is called only by the BFF and needs the server credential `KNOWVIA_IDENTITY_TOKEN` (32 to 256 characters, different from the bootstrap token; unset gives 503 `AUTH_NOT_CONFIGURED`, a wrong value 401). `IDENTITY_ISSUERS` is an exact-string allow-list (unset: every request is refused with 400). Body `{ issuer, subject (1-255), displayName (1-80), contactEmail? (320) }`. In one transaction under an advisory lock on `sha256(issuer + LF + subject)`: an existing active identity gets a new session for its adult's oldest active owner household (200, `returning: true`); a revoked identity or inactive adult is 401; an unknown identity creates adult, household, owner member and identity (201, `returning: false`). A session-cap refusal (429) rolls the whole transaction back, so no orphan adult is left. Only the hash of the subject is stored; the audit event for a new identity carries no issuer or subject; the route logs nothing. `POST /households`, the Host/Origin guard, CORS, the rate limiter, the session TTL and the session cap are unchanged.
  - *Threat model.* Account takeover: the key is issuer plus subject, never an e-mail address or name, and issuers come from the allow-list, so an unlisted provider cannot mint an identity. Enumeration: only a caller holding the credential can reach the route, and the BFF is the only holder. The credential holder can learn whether an identity exists (the `returning` flag, 201 versus 200, and 401 versus 404 all reveal it); nobody else can. Token leakage: provider tokens go to the BFF only, which seals them; this API never receives them, and the returned session token is sent with `Cache-Control: no-store`. Replay: the BFF checks the OIDC state and nonce before it calls this route; this route trusts an authenticated BFF and cannot detect replay itself. The bootstrap token is refused on this route and the identity credential is refused on `POST /households` (separate secrets, checked in config and in `TenantAccessService`). Accepted or open:
    - (a) A revoked identity is permanently burned (`UNIQUE(issuer, subject_sha256)` plus `revoked_at`). A returning adult with no active owner household (with a member row) gets 404 on every sign-in; there is no re-register path. No route revokes an identity; it is done in SQL only.
    - (b) The subject is hashed with plain sha256, with no secret pepper. Someone who leaks the table and already knows an (issuer, subject) pair can confirm it is a member. Accepted for now; an HMAC with a server key is a later option.
    - (c) First sign-in holds the `household_none` and `session_capacity` advisory locks until commit, which serialises first sign-ins. Fine at prototype scale.
    - (d) The credential has no rotation overlap (one value at a time), and a stolen credential lets its holder mint sessions for any subject, so it must stay server-side only.
- **D4. Two consent moments.** Keep the document; read these N documents (U3). A reading grant covers only documents that exist when the user consents.
- **D5. Scanning is on in hosting** (`DOCUMENT_SCAN_MODE=clamd`, U4). Until then the UI says documents wait for security checks.
- **D6. Read-only list routes.** `GET /api/v1/households/{id}/cases` and `/consents` return the caller's own records, bounded (limit 1-100, default 50, newest first, `truncated` flag), after `requireHousehold`. Cases never expose estimate, currency or member. Consent status is computed in SQL with the same `julianday` comparison as `requireActive`, so a NULL expiry reads as active (no expiry) and an unparseable expiry reads as expired. The cases list returns only cases the caller opened (`opened_by_adult_id`), not cases they only participate in. No new error codes.
- **D7. `member_card` is an accepted upload kind.** The database already allowed it. Other kinds stay refused.
- **D8. Voice intake is a contract only** (`voice-intake/v0`). Prefill values are `extracted_unverified` or `unknown`, never verified. No audio is captured.
- **D9. Read-back route for values (U5 approved; built in run V3a). Passages follow in V3b.** This changes the AI.md line "No route returns OCR text": no route serves raw OCR text or PDF bytes, but `GET /api/v1/cases/{caseId}/read-facts` returns bounded, labelled values from the caller's own read documents. It uses no model and stores nothing new. Gates, in order: the document-route case lookup (a missing and a foreign case are the same 404), the `source_pack` field (403 `FIELD_ACCESS_REQUIRED`), then `DOCUMENT_READBACK_ENABLED` (on only when exactly `true`, else 503 `READBACK_DISABLED`; independent of `POLICY_EVIDENCE_ENABLED`, and it never opens the paid Gemini route; checked in the service via `readbackEnabled(env)`, not in the `readServerConfig` object).
  - *Which documents.* Active documents of the case only. A document with a newer version is listed under `excluded` as `superseded`; a document being deleted (not `active`) is absent. A document is read only if its latest OCR job has succeeded and every succeeded `sarvam` job whose stored pages would be returned (`OcrRepository.getJobsHoldingPages`, the same filter as `getDocumentBlockPages`) still has a stored reading grant that passes `OcrRepository.getReadyDocument` with disclosure `{ consentGrantId, requestedByAdultId, recipient: 'sarvam' }`. This is re-checked on every request and never taken from the job row. Any job from another provider, a missing or in-flight job, or incomplete pages gives `not_read`. A grant past its expiry (not revoked) gives `reading_permission_expired`; a revoked, erased or non-matching grant gives `reading_permission_withdrawn`. Tests prove the check decides: an expired grant with the pages still stored, and a job whose requester is not the uploader, both hide the values.
  - *What is returned.* The deterministic extractor (`extractFields`) is applied to the stored block pages for insurer, plan name, the policy period, base sum insured, room rent, ICU limit, co-payment and the three waiting periods. Each field is `{ field, topic, value, state, page, quote }` with `state` one of `extracted_unverified`, `conflicting`, `unknown` (never `verified`). The response is labelled `read_not_checked`. Nothing is logged.
  - *Data minimisation.* Policy number, policyholder name, insured members and premium are never returned. The first three are extracted internally only to be hidden, together with the household's known identifiers (`loadKnownIdentifiers`) and each word of a name. A value longer than 60 characters, or one that is or contains such a string, is returned as `unknown` with no value, page or quote. A quote is the least text that will do: in a table block, only the matched label cell and value cell (located by the field's own label pattern, never the rest of the row); in any other block, the sentence holding the value. Identity strings inside it become `[hidden]`; it is cut to 160 characters or fewer around the value; it is null when it cannot be located with certainty. A greeting captured whole by the extractor (for example "Dear Asha, ...") is too long to count as a name, so a name that appears only there is hidden only if the household's known identifiers hold it.
  - *Erasure.* Revoking the reading grant already erases the pages, blocks and clauses (existing logic, proved by a test); the route then reports `reading_permission_withdrawn`. One additive read helper pair, `OcrRepository.getLatestJobForDocument` and `getJobsHoldingPages`, supports it.
  - *Open before member invites ship.* Cross-adult viewing is gated by the case subject's `source_pack_metadata` grant (the `source_pack` field), while the per-document check uses the uploader's own `sarvam` grant. With one owner per household these coincide; they must be revisited before member invites exist.
  - *Limits.* TPA helpline and member id are not extracted (follow-up); the emergency path stays "Call the helpline printed on your health card". Recall is low outside the evaluation policies; chips fall back to "Not found yet". A conflicting field returns only the primary value. Legal and medical wording is DRAFT.
- **D10. JPEG/PNG intake by conversion to a one-page PDF: pending U10.** Nothing is built.

## Consequences

Additive code only: one expand-only migration (017, D3), no new dependency, no change to existing consent, tenant, audit or erasure logic. Deferred: U6 (stored confirmed renewal date), U7 (Gemini top-up), U8 (data residency; synthetic data only until decided). Before any open sign-up with paid OCR (U9), a per-household page cap or subject allow-list is needed; it is not part of this change.
