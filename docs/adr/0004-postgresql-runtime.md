# ADR 0004: PostgreSQL runtime and schema translation

- Status: Accepted for Section 3 (P1-B), branch `claude/p1-postgres`
- Date: 2026-10-16
- Builds on: ADR 0002 (persistence port)

## Context

The runtime uses `node:sqlite` with six SQLite migrations. The plan requires all runtime persistence on PostgreSQL. The owner chose Homebrew PostgreSQL for local work. No production host, version or workload numbers exist.

## Decisions

- **D1 Version.** PostgreSQL 17 locally (Homebrew `postgresql@17`) and in CI (`postgres:17` service image pinned by digest). PostgreSQL 14 (also installed) reaches end of life in November 2026. The schema may use features up to 17 (for example `IS JSON`). The production version is decided with the Azure owner.
- **D2 Baseline.** PostgreSQL has its own numbered migrations in `src/backend/database/postgres/migrations/`. The first migrations reproduce the final state of SQLite 001–006; PostgreSQL never replays the SQLite rebuild steps. S3.2 removes the SQLite runtime from `src/`. S3.3 removes the SQLite migration files (git history keeps them) and keeps the SQLite export script under `scripts/`.
- **D3 Types are preserved, not upgraded.** `TEXT` stays `text`; `INTEGER` becomes `bigint`; the two rowid keys (`workflow_events.id`, `audit_events.id`) become `bigint GENERATED BY DEFAULT AS IDENTITY`; 0/1 flags stay `bigint` with their `CHECK`; JSON stays `text` with an `IS JSON` check where SQLite checks `json_valid`; timestamps stay ISO-8601 UTC `text` with their existing checks. Reason: application code reads these values as strings and numbers today, and the plan forbids changing domain meaning through type coercion. Native `timestamptz`, `boolean` and `jsonb` need a later expand migration and their own ADR.
- **D4 Collation.** Databases use the `C` collation, which orders bytes like SQLite's default `BINARY`. Schema validation reports a database with another collation as invalid.
- **D5 Dialect.** SQLite `LIKE` is case-insensitive for ASCII; PostgreSQL `LIKE` is not. Each `LIKE` keeps its SQLite meaning explicitly. `GLOB`, `julianday`, `strftime`, `json_*`, `INSERT OR …` and `changes()` are translated one by one, with a test where behaviour could differ.
- **D6 Triggers.** Each SQLite trigger becomes a PL/pgSQL trigger function with the same name, timing, event and condition. `RAISE(ABORT, 'msg')` becomes `RAISE EXCEPTION` with the same message. The critical-trigger list is validated on PostgreSQL as it is on SQLite.
- **D7 Migration runner.** `schema_migrations (version, checksum, applied_at)` as today. The runner holds a session advisory lock for the whole run, applies each file in its own transaction, records its SHA-256 and refuses to start if an applied file changed.
- **D8 Connections.** `pg.Pool` built from a server-only `DATABASE_URL`. Every connection sets `statement_timeout`, `lock_timeout`, `idle_in_transaction_session_timeout` and `application_name`. Defaults are configuration, not capacity claims.
- **D9 Tests.** `TEST_DATABASE_URL` points at a server where the test role may create databases. The harness migrates one template database per migration digest (under an advisory lock) and clones a fresh database per test from it. Without `TEST_DATABASE_URL`, PostgreSQL tests are skipped with a visible reason; CI sets `REQUIRE_POSTGRES=1`, which turns a missing URL into a failure.

## Consequences

- S3.2 must map PostgreSQL SQLSTATE codes (class 23, `P0001` from triggers) to the existing coded client errors and never expose driver messages.
- Concurrency moves from SQLite's single writer (`BEGIN IMMEDIATE`) to row locks. Claims, idempotency and revocation need explicit locking and concurrency tests (S3.2).
- Native types, partitioning and read replicas are out of scope until measured need.

## Rollback

S3.1 is additive (runtime still SQLite): revert the merge. After S3.2, revert to return to SQLite; no production data exists.
