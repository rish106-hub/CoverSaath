# ADR 0037: Hand insurer work to FSS as an asynchronous task, with mapped insurer, product and UIN tables

- Status: Proposed (2026-11-18). Owner direction taken in chat; design not yet built. Not reviewed. Builds on ADR 0034 (FSS as the insurer tier) and ADR 0036 (unchecked insurer facts). FOR LEGAL REVIEW: nothing here changes consent wording, but the data that leaves CoverSaath is named below.

**Context.** Today CoverSaath reads FSS (the separate `insurance-data-api` repository) in a job (`holding.fetch_reference`): it asks FSS to match the confirmed product, reads facts, and writes `ida_wording` rows. It waits on FSS inside the job, with a timeout, a breaker and a cache. FSS already has a worker, webhook settings and webhook deliveries, and a database of insurers, aliases, products, versions, documents and facts. Two problems show in the live test of a real health policy:
1. Product terms (room category, restoration, ICU, cashless) come only from the insurer tier. When FSS has nothing for the product, chat has nothing to fall back to, and CoverSaath cannot ask FSS to go and get it.
2. The names that tie a household's holding to an FSS product are matched by text at read time. There is no stored, reviewable mapping of insurer, product name and UIN.

**Decision.**
1. **Handoff, not a read.** CoverSaath sends FSS a task and carries on. `POST /v1/handoffs` (FSS) takes an idempotency key and identifiers only: an opaque CoverSaath request id, the insurer name as the person confirmed it, the product name as confirmed, optionally the UIN. It answers `202` with an FSS `handoff_id`. FSS does the rest on its own worker: resolve the insurer (alias table), resolve the product and the version, fetch or parse the wording if the source-rights register allows it, extract facts, and run its own review. No document of the household, name, number or policy text leaves CoverSaath.
2. **Result by signed notice, facts by pull.** When the handoff reaches a final state (`matched`, `no_match`, `needs_review`, `unavailable`, `rights_blocked`), FSS sends a signed webhook (HMAC over timestamp and body, replay window) to CoverSaath's receiver. The notice carries the request id, the handoff id, the final state and the FSS version id only. CoverSaath then pulls `GET /v1/versions/{id}/facts` through the existing client and writes `ida_wording` rows through collate, as ADR 0034 and ADR 0036 already define. `GET /v1/handoffs/{id}` is the fallback when no notice arrives (one poll per hour per open handoff, bounded).
3. **CoverSaath side.** A table `fss_handoffs` (household id, holding id, request id, FSS handoff id, state, attempts, last outcome code, created, decided; RLS on, `anon` and `authenticated` revoked, identifiers and enum codes only) and an outbox job `holding.fss_handoff`. The existing `fetch_reference` reader stays, behind a flag, as the fallback until the handoff path has run clean; then it is removed. The adapter lives in `src/integrations/insurance-data/` (the one allowed entry point). Revocation, document deletion and holding deletion erase the handoff row; a notice for an erased holding is dropped and counted.
4. **Mapped, dynamic data model (FSS owns it).** FSS keeps canonical tables: `insurers` (id, legal name, regulator id), `insurer_aliases` (alias, normalised alias, insurer id, source), `products` (id, insurer id, name, line), `product_uins` (raw UIN as printed, normalised UIN, product id, valid from and to, source), `product_versions`, `documents`, `facts`. A UIN never leaves FSS except to CoverSaath's server, and never reaches a page (unchanged rule). New insurers and products are added by import jobs and by the review queue, with no code change. CoverSaath stores only references: `policy_holdings.fss_product_id`, `fss_version_id`, and the match outcome, in one mapping table `holding_fss_links` (holding id, FSS product id, version id, matched by `alias|uin|manual`, confidence code, matched at). The person-facing names stay the ones the person confirmed.
5. **Insurer, product and UIN set up in parallel.** The backfill of UINs for the roughly 49 insurers, the insurer alias list and the product registry import (FSS `real product registry importer`) are one FSS workstream with its own acceptance check: every product in the registry has an insurer and at least one UIN row, or is listed as `uin_missing` in the coverage report (`/v1/data-coverage`). CoverSaath's holding matcher reads only this mapping.
6. **Failure and cost.** The handoff never blocks the upload, the plan choice or chat. A `no_match`, `rights_blocked` or `unavailable` outcome leaves the holding at `wordingState = missing` with the reason code already defined by migration 066. FSS retries on its side; CoverSaath retries the outbox send with backoff, at most three attempts, then marks the handoff `failed` and lists it for support. No model call is made by CoverSaath for this path; any model use is inside FSS under its own budget and its signed extraction contract.

**Consequences.** The household path stops waiting on FSS, and FSS can parse, review and extract on its own schedule and answer later. The cost is a second moving part (outbox, receiver, signature handling) and a period of two paths. Wording page text is still not served by FSS, so chat still cannot quote the insurer's page; that stays open until FSS exposes page text under the rights register.

**Build order (each step shippable on its own).**
1. Contract: OpenAPI for `POST/GET /v1/handoffs` and the webhook body in FSS `docs/contracts`, plus a mock FSS server in CoverSaath tests.
2. FSS: handoff table, endpoint, worker stage, signed webhook delivery (reuse webhook settings and deliveries).
3. CoverSaath: migration for `fss_handoffs` and `holding_fss_links`, outbox job, receiver route with signature check, erasure paths and their tests.
4. Mapping workstream: insurer aliases, UIN backfill and product registry import, with the coverage report as the check.
5. Cut over `fetch_reference` to the handoff behind a flag; run on one holding; then default on; remove the synchronous reader later.

**Alternatives rejected.**
- Keep the synchronous reader and only lengthen its timeout: it still blocks the job and cannot make FSS go and fetch.
- Move FSS code into CoverSaath: this merges two rights and retention regimes (ADR 0034 rejected an own wording store for the same reason).
- Send FSS the household's PDF: personal data would leave CoverSaath for no gain; identifiers are enough to find the product.
- Push all facts in the webhook: large payloads, harder replay and signing; a notice plus a pull is simpler to verify.

**Open questions for the owner.** Which FSS environment receives the webhook (Fly URL and secret ownership). Whether FSS may fetch a missing wording from the insurer's public site on its own, or only parse documents already in its store (source-rights register). Who reviews `needs_review` outcomes.

**Implementation notes** (review fixes, pull and pack).
- Redrive: the poll re-queues the pull of a matched handoff whose job died (counter `pull_attempts`, migration 070, cap 72, then outcome `pull_gave_up`), and re-pulls a pulled pack whose cached facts are 24 hours stale. A re-pull that answers 404 `pack_not_available` deletes that version's cache rows and re-collates, so rights withdrawal reaches the person's rows.
- Pack facts are always `extracted_unverified` (ADR 0036), even when FSS flags `independently_verified`: the published pack has no conditions or exceptions list yet. Revisit when FSS adds them. `clause_ayush` maps only as not checked.
- The two public cache rows are written before the household-locked link transaction. One poll row failing never stops the others.
