# ADR 0013: Column encryption, document bytes in the database, stored profile answers and RLS

Status: proposed (2026-11-01). Synthetic data only. All consent, privacy and notice wording named here is DRAFT and needs legal review. Related: ADR 0011 (Supabase + Fly), ADR 0012 (UI journey), migrations 016 to 020. Owner request: "store every form of data in the database; apply encryption and RLS to all relevant rows".

## Context

- Document bytes were encrypted (AES-256-GCM, `CSD1` envelope) but written to the server filesystem. A Fly machine filesystem is not durable across redeploys without a volume.
- Names, e-mail, phone, OCR text, extracted clauses, answers and fact values sat in PostgreSQL as plain text, protected only by the provider's disk encryption.
- Every table already has row level security enabled with no policy (migration 016, 017), and the Data API roles hold no privilege. The backend connects with a direct owner role that bypasses RLS.
- The UI asks four questions per case (who is covered, where the user lives, the renewal month, a few yes/no answers) and had nowhere to store the answers.

## Decisions

- **D1. Column encryption in the application.** `src/backend/security/column-crypto.js` seals a text column as `enc1.<keyId>.<nonce>.<tag>.<ciphertext>` (AES-256-GCM, 12-byte nonce, base64url). The additional authenticated data is `table.column.rowId`, so ciphertext cannot be moved to another row or column (tested). Writes always seal. A value without the `enc1.` prefix is legacy plaintext and is read as is until `scripts/encrypt-existing-rows.mjs` has sealed it; `DATA_ENCRYPTION_LEGACY_PLAINTEXT=false` then refuses it. Repositories seal on write and open at their edge; the few direct SQL readers (`coverage-analysis-port.js`) open explicitly. SQL never searches a sealed column.
- **D2. Keys.** `DATA_ENCRYPTION_KEY_BASE64` (32 bytes) with `DATA_ENCRYPTION_KEY_ID` (default `k1`) and optional `DATA_ENCRYPTION_PREVIOUS_KEYS_JSON` for rotation. The key is required when `NODE_ENV=production` or `DATA_ENCRYPTION_REQUIRED=true`; server start and service construction fail with the coded error `DATA_ENCRYPTION_KEY_REQUIRED` otherwise. Outside production with no key a fixed development key (`dev`) is used; it is public in this repository and protects nothing. Rotation: set the new key and id, move the old key to the previous list, run the script with `--rotate`; old rows keep reading throughout. The key is held by the application process, so a database dump or a provider operator without the key reads ciphertext only. A compromised application process, or an operator who holds both the key and the database, reads everything: this is encryption at rest in the application layer, not a defence against a compromised server. The key must be stored in the host's secret store, never in the repository. Losing the key loses the data in the sealed columns.
- **D3. Which columns.** `adult_users` (display name, contact e-mail, contact phone), `households.display_name` (it carries the person's name), `household_members.display_name`, `source_pages` (extracted text and the stored blocks, which hold the same text), `ocr_jobs.result_json`, `policy_clauses` (title, text), `policy_answers.answer_json`, `evidence_facts.value_json`, and `profile_answers.value_ciphertext` from the start. Not sealed in this pass (follow-up): `policy_answers.question`, `coverage_parameter_*` and `proposed_parameters` values and labels, `workflow_tasks`, `audit_events`, `integration_outbox`, `idempotency_keys`, `curated_product_submissions` and `catalogue_reviews` JSON. Dates of birth and `relationship_label` also stay plain. Audit payloads were already counts-only.
- **D4. No blind index.** No code path looks a row up by e-mail, name or phone (sign-in uses the hashed `(issuer, subject)` pair), so no keyed blind-index column was added. Add one with the lookup that needs it.
- **D5. Migration 019 relaxes checks, nothing else.** A sealed value is not JSON, so the single-column `IS JSON` checks on `ocr_jobs.result_json`, `source_pages.blocks_json`, `evidence_facts.value_json`, `policy_answers.answer_json` and the plaintext length caps on `policy_clauses.title` and `text` are replaced by looser `length()` caps sized for the envelope. Validity is enforced where the value is opened and parsed (for example `parseStoredBlocks` fails closed). No row, column or other constraint changes; the file is safe to run twice.
- **D6. Search over sealed clauses runs in the application.** `ClauseRepository.searchClauses` pages through the clauses of the consented documents of one household and case (200 per page, at most 10,000 scanned), opens them, and ranks in `clause-text-search.js` (Porter stemming, English stop words, any-term match, term count then frequency then proximity). It replaces the PostgreSQL `tsvector` query, which would need plaintext in SQL. The ranking is not identical to `ts_rank_cd`; the existing retrieval and passage suites pass unchanged. Consent, masking and identity-drop behaviour are untouched because they sit above the repository.
- **D7. Backfill and rotation script.** `scripts/encrypt-existing-rows.mjs [--dry-run] [--rotate] [--batch=N]` seals legacy rows, keyset-paged, one transaction per batch, counts only in its output, idempotent (a second run changes 0 rows). It must run as the table owner: the append-only or immutable stores (`evidence_facts`, `policy_clauses`, `policy_answers`, and `source_pages.blocks_json`) are protected by triggers, and each batch disables exactly that trigger, updates, and enables it again inside the same transaction, so an error restores it. It takes a short `SHARE ROW EXCLUSIVE` lock per batch: run it in a quiet period.
- **D8. Document bytes in the database.** Migration 020 adds `document_blobs (document_id PK, storage_key unique, household_id FK, envelope bytea <= 16 MiB, created_at)`. `createEncryptedDatabaseByteStorage` implements the interface of the filesystem adapter and writes the identical `CSD1` envelope (shared `document-envelope.js`), so bytes are encrypted in the application before they reach PostgreSQL and a document moves between backends without re-encryption (tested both ways). `DOCUMENT_STORAGE_BACKEND=database|filesystem` (default `database`) picks the primary; the other stays readable through `createFallbackByteStorage`, and a removal clears both, so a switch or rollback loses nothing. No mass migration of existing files is built. The envelope format of existing files is unchanged.
  - *No foreign key to `document_uploads`.* Intake stores the bytes first and creates the document row afterwards, so a foreign key would reject the first insert, and reordering intake was out of scope. Erasure is instead done by a trigger (`document_blobs_erase_on_document_erasure`) that deletes the blob in the same transaction in which a document enters `deletion_requested` or `deleted` (consent revocation, erasure, malware block); the existing orphan sweep removes a blob with no live document row. `household_id` is kept so blobs can be located and erased by household.
  - Blobs are never listed or returned by any route; the adapter is reachable only by the document services.
- **D9. Stored profile answers.** Migration 018 adds `profile_answers (case_id, field_key, value_ciphertext, source = 'user_stated', ...)` with `UNIQUE (case_id, field_key)`, a closed list of seven field keys (`covered_people`, `city`, `state`, `renewal_month`, `has_employer_cover`, `has_personal_policy`, `has_top_up_policy`), no free text beyond a city or state name, no diagnoses, no identity numbers. Routes: `GET`, `PUT` (idempotent, `null` removes one answer) and `DELETE` on `/api/v1/cases/{caseId}/profile-answers`. The case must belong to the caller's household (a foreign or missing case is the same 404) and the caller must be the adult who opened the case or the subject member's adult. Answers are the user's own statements: they carry no evidence state, are never `confirmed` or `verified`, and the model never writes them. Audit events are counts-only. Erasure: the `DELETE` route, `ProfileAnswerRepository.eraseForCase` and `eraseForHousehold` (the paths a future case or household deletion calls). There is no case or household deletion in the code today; revoking a document consent does not erase profile answers because they are not derived from a document.
- **D10. RLS.** Row level security here is deny-by-default against the Supabase Data API: enabled on every table with no policy, the API roles revoked. **Household isolation is enforced in application code** (ownership checks on every protected read and write), not by RLS; per-household policies were not built because the owner did not choose them. `tests/rls-coverage.test.mjs` asserts every table in `public` has `relrowsecurity = true`, that `anon` and `authenticated` hold no privilege on any table, view or sequence, and that the check is not vacuous; `validatePostgresSchema` reports the same in `db:init` and `/api/v1/ready`. Both new tables enable RLS and revoke the API roles in their migrations.
- **D11. `FORCE ROW LEVEL SECURITY` was not added.** `FORCE` only changes behaviour for a table owner without `BYPASSRLS`; an owner or superuser with `BYPASSRLS` ignores it. The migrator and the runtime role are chosen by the host (on Supabase the direct `postgres` role, which bypasses RLS), and this repository cannot know at migration time that the runtime role bypasses. If it did not, `FORCE` with no policy would lock the backend out of every table. Adding it would therefore either do nothing or break the service. Re-open this decision if a dedicated non-bypass runtime role is introduced, together with per-household policies.

## Review fixes (2026-11-01, after independent review)

- **Length padding.** AES-GCM ciphertext length equals plaintext length, so a short stored value (a profile answer) leaked its size. New writes use the `enc2.` envelope: the plaintext is framed with a 4-byte length and zero-padded to a bucket (32 bytes doubling up to 4 KiB, then multiples of 1 KiB). Profile answers are padded to a fixed 256 bytes, so all seven fields and every allowed value store the same length (tested). `enc1.` envelopes from the first build still open; `encrypt-existing-rows.mjs --rotate` upgrades them. Buckets still reveal a size class for long text; that is accepted.
- **Development key.** The public development key is refused for any `DATABASE_URL` whose host is not loopback, as the configured key, and (when a key is required) as id `dev` or by value in `DATA_ENCRYPTION_PREVIOUS_KEYS_JSON`. The backfill script requires a real key (it forces `DATA_ENCRYPTION_REQUIRED`) unless `--allow-development-key` is given, and the flag never lifts the remote-database refusal.
- **Clause search is bounded.** Suffix tables are sorted once, stems are memoised in a bounded map, scoring is one pass with no token arrays, pages are 100 clauses, the scan cap is 2,000 clauses and 3 s, and the event loop is released between pages. A cut-short search sets `truncated`, which the passages response carries as `truncated: true` (absent otherwise).
- **Migration 021** (019 is unchanged) adds `col IS NULL OR col ~ '^enc[12][.]' OR col IS JSON` to the four JSON columns and requires an envelope in `profile_answers.value_ciphertext`. Name and text columns stay unconstrained until every environment is backfilled.
- **Smaller fixes.** The orphan sweep pages the whole blob table by key. A backfill batch that fails rethrows the original SQL error (the rollback restores the disabled trigger). The 100,000-character clause text and 200-character title caps, which the database could no longer enforce on a sealed value, are enforced in `validateClause` and `ClauseRepository.saveClauses`.

## Consequences

- Positive: a database dump, a provider operator, or a leaked backup reads ciphertext only for the listed columns and for document bytes; uploads survive a Fly redeploy without a volume; the Data API shield is tested, not assumed.
- Cost: a lost `DATA_ENCRYPTION_KEY_BASE64` or `DOCUMENT_ENCRYPTION_KEY_BASE64` loses that data. A decryption failure answers a coded 500 (`COLUMN_DECRYPTION_FAILED`) for the affected read and never includes a value. Clause search reads and decrypts up to 10,000 clauses per query (bounded). Document bytes add database size and backup size (16 MiB cap per document); the 512 MB Fly machine and the Supabase plan were not re-measured, so this is unmeasured.
- Risk: the development key is public. Never run a shared or hosted database without a real key (production enforces it).
- Rollback: set `DOCUMENT_STORAGE_BACKEND=filesystem` (database blobs stay readable through the fallback). Sealed columns stay readable only by code that has the key; rolling the code back to a build before this change makes sealed columns unreadable, so before such a rollback run the backfill in the reverse direction (not built; the test helper `downgrade` shows the shape) or restore from a backup. Plaintext written by older code keeps reading with this code.
- Needs an independent read-only review before commit (migration, security, data).

## Addendum D2 (2026-11-06): the remaining user-derived columns, migration 030

Closes the "not sealed in this pass" list of D3. Synthetic data only; consent, privacy and notice wording stays DRAFT for legal review.

- **Sealed now (`enc2.`, AAD `table.column.rowId`):** `household_members.relationship_label`, `date_of_birth`; `policy_answers.question`; `document_uploads.original_filename`; `policies.policy_number_masked`, `policy_version`, `starts_on`, `ends_on`; `policy_members.member_reference_masked`; `coverage_parameter_observations.value_json`; `coverage_parameter_resolutions.resolved_value_json`; `proposed_parameters.label`, `value_json`; `workflow_runs.input_json` (source excerpts); `workflow_tasks.input_json`, `output_json`, `last_error_message`; `workflow_events.event_payload_json`; `idempotency_keys.response_json`; `integration_outbox.payload_json`, `last_error`; `integration_webhook_events.payload_json`, `processing_error`; `coverage_graph_snapshots.graph_json`; `coverage_graph_nodes.label`, `entity_ref`; `reviewer_findings.message`, `resolution_note`; `consent_revocations.reason`; `catalogue_reviews.fact_json`; `ocr_jobs.error_message`; `source_pages.provenance_json`.
- **Stated estimate.** `service_cases.stated_estimate_minor` (a number) cannot hold an envelope. Migration 030 adds `stated_estimate_ciphertext`; new rows write only that (padded to a fixed size), the bigint stays `NULL`; the backfill moves old values and clears the bigint in the same statement. `CaseRepository.get` and `TenantAccessService.requireCase` return the amount as `stated_estimate_minor` as before.
- **Blind index (D4 applied).** Erasing a document deleted its upload idempotency record by reading `response_json` in SQL. The response carries the filename and is now sealed, so `idempotency_keys.document_index` holds `HMAC(blind key, document id)` (`crypto.blindIndex('idempotency_keys.document', id)`), indexed partially. Legacy plain rows are still matched on the id inside the JSON. The backfill writes the index in the same UPDATE that seals the response (one transaction per batch) and `--rotate` recomputes it under the new key; a record that cannot be decrypted is counted as `unreadable` in the report, never skipped silently.
- **Row ids in the AAD.** `workflow_events` takes its id from the sequence before insert, so the payload is bound to its own row. Composite keys (`idempotency_keys`, `policy_members`) use a length-prefixed row id, so no two key pairs give the same AAD.
- **Kept plain on purpose** (each with a reason in `tests/column-audit.test.mjs`): ids, timestamps, digests and numbers; closed vocabularies; `audit_events.event_payload_json` (counts only; the one free-text value, the revocation reason, now appears as `reasonProvided` instead of the text); `ocr_jobs.authorization_json` and `policy_answers.document_ids_json` (ids and flags, read in SQL by revocation erasure); `evidence_facts.permitted_viewers_json` (adult ids); curated product and insurer tables (public insurer wording, ADR 0010).
- **Checks.** Migration 030 replaces each single-column `IS JSON` / length check on a sealed column with one check: `NULL OR (enc envelope [AND looser cap]) OR (the old plaintext rule)`, so legacy plaintext keeps its old integrity until sealed. The checks are added `NOT VALID` (the runner uses one transaction per file, so a scan would hold the DDL lock) and the backfill runs `VALIDATE CONSTRAINT` for them in separate statements. Name and text columns stay unconstrained until every environment is backfilled. Migrations 019 and 021 are untouched.
- **Backfill.** `scripts/encrypt-existing-rows.mjs` covers the new columns (composite keys, the exact blocking triggers per table, the estimate move, the document index), idempotent. New `--unseal --i-understand-this-writes-plaintext` is the reverse direction for a code rollback; by default it unseals the D2 columns only (`--include-e1` adds the earlier ones). Undecryptable values are left alone and counted (`unreadable`, exit code 3). Erasure never aborts on an undecryptable run input: such a run is erased whole (`input_json` set to NULL, run revoked).
- **Audit test.** `tests/column-audit.test.mjs` classifies every public column; an unlisted new column fails it.
- **Rollback:** `docs/runbooks/migration-030-rollback.md`.
- **Erasure never depends on a readable sealed value.** An undecryptable run input erases the run whole. An undecryptable document filename reads as `null` (`originalFilenameUnreadable`), so DELETE, the deletion worker and the inventory still work. The deletion-inventory and profile-answers DELETE routes read the case with `tolerateUnreadable`, so a damaged stated estimate does not stop them; every other reader still fails closed on it (money is never read as zero). Document erasure matches the upload idempotency record on the index under every key of the ring (`blindIndexes`), so it works between a key change and the end of `--rotate`. The backfill and `--rotate` stop with `BACKFILL_LEGACY_PLAINTEXT_REFUSED` when `DATA_ENCRYPTION_LEGACY_PLAINTEXT=false` (they have to read plaintext).
- **Third review.** The household of a case is read from the row without opening the sealed estimate (revocation, stop and erasure only need the lock). `requireCase` checks the household before it decrypts (no existence oracle). The catalogue service opens the case row. Unreadable filenames are counted and reported through `onUnreadable` (table and column only; the server logs a `sealed_value_unreadable` warning). A document erasure puts the number of sealed upload records it could not attribute (no index) into the `document.bytes_deleted` audit payload as `unattributedUploadRecords`; it never reads them.
