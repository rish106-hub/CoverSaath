# ADR 0025: Policy facts and fact evidence (policy facts, slice 2)

- Status: Proposed (build complete, not independently reviewed). Synthetic data only. Wording about consent, privacy and retention below is an engineering reading and is **FOR LEGAL REVIEW**.
- Numbering: 0024 is the highest ADR on the branch this stacks on (slice 1, PR #89); 0007 is skipped (see `AI.md`).
- Related: ADR 0003 (AI authority), 0008 (evidence-first), 0009 (household confirmation is `reported`, never `proven`), 0013 + addendum D2 (column encryption), 0014 (limits), 0024 (policy profile, slice 1), `src/backend/AGENTS.md`, `src/backend/database/AGENTS.md`.
- Scope: migration `044_policy_facts.sql` (`policy_facts`, `fact_evidence`), `src/features/policy-facts/`, the `policy_facts.extract` job, `GET /api/v1/documents/{id}/policy-facts`. Slice 1 (`042`, `043`) is a prerequisite.

## Context

After a document is read the app wants every normalised datapoint it prints (sums and premiums, the policy period, waiting periods, copay, no-claim bonus, payment events, the seller, member ages, clauses) stored once, each tied to the place in the document it was read from, so a later screen or check can show the number and where it came from.

## Decisions

**D1. Two new tables, expand-only (044).** `policy_facts` holds one row per (extraction run, fact type, scope key, ordinal). `fact_evidence` holds the places it is printed (`page`, `block_index`, `clause_id`, a sealed `quote_enc`, the page digest `source_digest`, a role `primary | corroborating | conflicting`). The migration is idempotent (`IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, drop-and-create triggers) and is tested twice in a row.

**D2. `fact_type` is text with a shape CHECK, not a SQL enum.** The closed vocabulary lives in `fact-types.js` and is validated in the application; a new type needs a code change and a test, not a migration. A drift test checks every type's registry key exists, and that a type maps to a registry key only if that key exists. `FACT_TYPE_TO_REGISTRY_KEY` is that map.

**D3. Exact money is sealed; only a coarse band is plaintext (decision of the open question).** Exact amounts, dates, the printed waiting-period unit, free text and every quote are sealed (`enc2`, AAD `policy_facts.<column>.<row id>`). Plaintext columns are coarse by design: `amount_band` (nine bands from under 10 thousand to 1 crore and over), `value_duration_days`, `value_percent_bp`, `value_bool`, `value_enum`, `value_ym` (year-month), `currency`. Rationale: an exact sum insured or premium plus a policy period can point at one household; a band, a day count and a year-month cannot. Analytics and the app's list screens work from the coarse columns without a key. The cost: no exact-amount query in SQL. An exact value is opened in the application only for a fact the owner reported.

**D4. Dropped from the plan, with the reason.** `value_hash` and `subject_ref` (no consumer; the blind index has no rotation tool, `column-crypto.js`), and `quote_digest` (a plain sha256 of a short quote such as "Sum Insured: Rs 5,00,000" can be guessed, which would undo the sealing). `fact_evidence.source_digest` stays: it is the sha256 of the whole stored page (`source_pages.page_sha256`), which is not guessable, and lets a later check tell whether the page the quote came from changed. Add any of the three back only with a named consumer and a rotation story.

**D5. Authority.** A deterministic reader and a model write only `extracted_unverified`, `conflicting` or `unknown` (a CHECK says it; the repository refuses anything else before the database does). `reported` is the owner's own statement (`origin = user_statement`, `confirmation_source = user_statement`, `confirmed_at`, `confirmed_by_adult_id`, ADR 0009) and is never `proven`. No code path writes `reported` in this slice; the table and its CHECKs are ready for the per-fact confirm route, which is a follow-up. All CHECKs are NULL-safe (a CHECK passes on NULL, so every operand is `IS [NOT] DISTINCT FROM` or `IS [NOT] NULL`).

**D6. Shape per value type.** A CHECK allows exactly the columns of the fact's `value_type` (`money`, `date`, `date_range`, `duration`, `percent`, `number`, `enum`, `bool`, `text`) and no other; an `unknown` or `conflicting` fact holds no value, no sealed text and no coarse column. The sealed canonical JSON is key-sorted.

**D7. Evidence verification (`evidence-verify.js`).** A fact is kept only when its quote is a literal substring of the cited chunk's text (NFC), on the cited page and block, and its value parses from that quote with the type's normaliser to the same value. Otherwise it is dropped with a reason code. Free text must be a literal piece of its quote. A model-proposed fact also needs a fact type the registry lets a model propose: `registryKey` set and `modelExtraction.allowed === true`. An unmapped type (seller, member ages, GST, payment total, specific-disease waiting) is deterministic-only. A seller registration number is never model-eligible (`data-purpose-registry.js` keeps `modelEligible` false).

**D8. Conventions (FOR REVIEW).** Money is INR in paise; lakh and crore are 100,000 and 10,000,000 rupees; a "per day" rate is refused as a plain amount. Dates are the printed calendar date, day-first for `dd/mm/yyyy`, with no time zone and no time (IST is the assumed calendar). A policy period is two dates in order, counted inclusively in days. Durations become days with a year of 365 days and a month of 30, and twelve months carry into a year first (36 months = 3 years = 1095 days; 2 years 6 months = 910 days); the printed amount and unit stay in the sealed value. Percentages become basis points. A no-claim bonus table gives one `ncb_tier` per year (scope `year_n`) and one `ncb_max`. A payment mode is a closed set (`upi`, `credit_card`, `debit_card`, `net_banking`, `cheque`, `cash`, `auto_debit`, `wallet`); a frequency word such as "annual" is not a mode. The seller type is a closed set; it is never inferred: no printed seller gives a fact in state `unknown` with no evidence, and `direct` needs the printed word.

**D9. Deterministic extraction (`deterministic-extractors.js`).** A fact is read only from a printed `Label: value` line or a table row `Label | value`. The label decides the type, the normaliser the value, the line is the quote. A line with two different values, a header-above-values table, a label with the value on the next line and a line over 500 characters are not read (left to the model path). Several different printed values for one fact give one `conflicting` fact with up to four conflicting quotes and no value; the same value printed twice gives one fact with corroborating evidence. Work is bounded: 4000 lines, 2000 chunks, 200 facts, 4 evidence per fact, normaliser input capped at 4000 characters. `scope_key` holds a policy-wide term label slug (a cataract waiting period, a no-claim year) or a member index (`member_1`); it never holds a person's name.

**D10. Hook and job.** The end of a new structuring commit (`PolicyStructuringRepository.#commit`, after its audit event, never on a replay) enqueues one `policy_facts.extract` job on `job_queue` in the same transaction, inside a savepoint so a queue failure never undoes the structuring result. The job is identifiers only: the document and household columns, the structuring grant id, and `{ normaliserVersion }`. `dedupe_key` is `pfx-` plus 40 hex characters of a sha256 of document, source version and normaliser version (dedupe holds only while a job is queued or running, so `ON CONFLICT DO NOTHING` on the facts is what makes a retry safe). The handler (`src/backend/jobs/policy-facts-handler.js`, registered in `src/server/worker.js` only while the flag is on) calls `PolicyFactsService.extract`, which reads the stored OCR pages through the shared consent gate (`readable-document.js`, the same gate as the policy profile), extracts, verifies and stores in one transaction. The transaction re-checks that the document is active, still at that source version and that its `document_processing` consent is current; a model-proposed run also awaits the model-grant check inside the transaction. A document that is no longer readable ends the job without writing (a permanent end, not a retry). Switched off or malformed jobs dead-letter at once.

**D11. Flag.** `POLICY_FACTS_ENABLED`, default off, exactly `true`; the same switch as the policy profile.

**D12. Model path is built but not wired to a model.** `PolicyFactsService.recordModelFacts` verifies and stores facts a model proposed. No model or provider call is made in this slice, and nothing calls `recordModelFacts` yet; wiring it to the structuring pipeline (privacy gate, Gemini grant, budget) is a follow-up that needs its own review. A deterministic run and a model run use different `extraction_run_id` suffixes, so both may hold a row for one fact type; a consumer must treat more than one current row for the same (type, scope) as unresolved.

**D13. Erasure.** The database deletes a document's facts and evidence when the document enters `deletion_requested` or `deleted` (trigger, migration 012 pattern; DELETE, not NULL, so an immutable row needs no escape hatch). Application paths: `ConsentRepository.eraseDerivedRunData` (consent withdrawn or document erased; deletes all facts of the affected documents, model-proposed ones too, because that path cannot tell which grant was withdrawn), `ErasureRepository` case and household paths, and the repository's own `eraseForDocuments`, `eraseForCase`, `eraseForHousehold`. Pending jobs are erased by the existing `job_queue` erasure. Counts-only audit. Registered in `data-lifecycle.js`, `data-purposes.js`, `data-purpose-registry.js`, `schema-expectations.js` (tables and triggers) and `column-backfill.js` (rotation re-seals `value_enc`, `raw_text_enc`, `quote_enc`; the immutable triggers are stepped past; `--unseal` skips them because the CHECKs refuse plaintext).

**D14. Read.** `GET /api/v1/documents/{id}/policy-facts`, owner adult only; a missing document, another household's document and a non-owner answer the same 404 `POLICY_FACTS_NOT_FOUND`. It lists current facts (superseded ones are hidden), bounded to 500, with the coarse columns and the evidence locators (page, block, clause, role). A sealed value and a quote are opened and returned only for a fact in state `reported`; every fact a reader wrote keeps them sealed in the response.

## Consequences and open points

- Immutability: a fact changes only by setting `superseded_by_fact_id` once, to a fact of the same document. Evidence is never changed. Rotation disables and re-enables the two immutable triggers inside the backfill, as it does for the other immutable tables.
- Revoking a model-only grant deletes every fact of the affected documents (D13). Whether withdrawing only the model grant should keep deterministic facts is an owner and legal decision (FOR LEGAL REVIEW); keeping them would need the revoke path to pass the grant's recipient.
- An evidence requirement ("a non-unknown fact has at least one primary evidence") is enforced by the repository in one transaction, not by a deferred constraint.
- Term-life: `applicableFactTypes(policyType)` returns the subset for `service_cases.policy_type`; extraction does not filter by it yet (a term-life schedule simply has no waiting-period labels).
- Not built: the per-fact confirm and correct route (supersession with `reported`), a BFF counterpart, and wiring `recordModelFacts`. The beta and BFF repositories need the matching read screen and a mock adapter for `GET .../policy-facts` before this is useful (standing rule: every backend change ships with its counterpart).
- Rollback: expand-only. Turn the flag off and revert the code; a synthetic-only database may drop `fact_evidence` then `policy_facts`. An applied migration is never edited; fix forward with the next number.
